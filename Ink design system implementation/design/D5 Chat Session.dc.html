Postgres vs Redis for job queues google / gemini-2.5-pro
6.2k tokens
We run about 40k background jobs a day (emails, image resizing, webhook retries). Already on Postgres 16. Is it worth adding Redis for the queue, or can Postgres handle it?

At 40k jobs a day, Postgres handles this comfortably. That is roughly one job every two seconds on average, and even a 20× burst stays well within what a single Postgres instance can dequeue with SELECT … FOR UPDATE SKIP LOCKED.

When Postgres is the better choice

  • Jobs are enqueued in the same transaction as the data they act on, so you never send an email for an order that rolled back.
  • One fewer system to back up, monitor and fail over.
  • Libraries like pg-boss, Graphile Worker and River give you retries, scheduling and dead-letter handling.

When Redis starts to make sense

  • Sustained throughput above a few thousand jobs per second.
  • Sub-millisecond pickup latency matters more than durability.
  • You already run Redis for caching and are comfortable operating it.

A minimal dequeue looks like this:

sql
UPDATE jobs SET status = 'running', locked_at = now()
WHERE id = (
  SELECT id FROM jobs
  WHERE status = 'queued' AND run_at <= now()
  ORDER BY priority, run_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING *; -- add a partial index on (priority, run_at) WHERE status = 'queued'

My recommendation: stay on Postgres, add the partial index, and vacuum the jobs table aggressively or partition it by day. Revisit Redis if p95 pickup latency passes 500 ms.
