# OP-007 — dormant PostgreSQL approved-skill registry

Base: `2b289c03877ac1a2af4188ecf8b0ac02ef7ba47b`. This additive slice implements the persistence seam of [the approved-skills contract](op007-skills.md). It does **not** enable skills in HTTP, Pi, the coordinator or desktop, nor complete OP-007. Only `skills-postgres.ts`, its source-named test and this document change. Existing repository/schema/core/service files and dependency symlinks are untouched.

## Storage and transitions

`PostgresSkillRegistry` implements `SkillRegistryStorage` over the existing asynchronous repository. Its constructor binds one **trusted, server-resolved scope**. Every `read(scope)` rejects a different scope before accessing the repository and fetches exactly one current generic record; absence means revision zero. There is no cache, list scan, second authority, SQLite fallback or synchronous bridge.

- Kind `op007.skills.registry.v1`, ID `JSON.stringify(['op007.skills', scope])`: strict schema-version-1 envelope containing scope and retained entries. The generic record's revision is the CAS revision (not a second counter).
- Each retained entry contains only root ID, relative directory, skill name, exact version, manifest digest and approval/active/revoked/deleted flags. No manifest/instruction/resource bodies, credential values, filesystem absolute roots, runtime paths or executable content are stored. Identifiers supplied by the trusted owner must themselves be nonsecret.
- The scope record is bounded to 1,024 **retained** pins, including tombstones; all strings and paths have the same limits/grammar as the existing skill contract. One bounded scope record makes entry/revision reads atomic and avoids unbounded list materialization. Generic repository callers or database administrators that bypass this writer are outside the integrity boundary; malformed stored envelopes fail validation, but no claim is made to bound arbitrary hostile database bytes before the existing repository deserializes a row.
- `(scope,name,version)` never changes its `(rootId,directory,digest)` identity. Every operation supplies the exact full pin and expected scope revision. Mismatches, stale revisions, overflow, extra fields, unknown operations and no-op transitions fail closed. Caller-owned input is parsed/copied and frozen before the first await.
- `approve` creates an approved **inactive** pin. `activate` atomically deactivates the previously active version of that name, leaving its approval and historical pin intact. `deactivate` stops new admissions without revoking an existing selection. Only one version per name can be active.
- `revoke` permanently clears approval/active and retains a visible revoked pin. `delete` is a logical terminal deletion: clear approval/active, set revoked, retain the hidden tombstone. These terminal entries cannot be approved, activated, reassigned or otherwise revived. There is deliberately no physical purge, tombstone reset or delete-after-revoke transition; both terminal operations already stop subsequent content loads. Publish a new version for changed content.

## Trusted writer and common-gate boundary

`AuthorizedSkillRegistryWriter` is a separate server-only capability. Construct it with the repository, current `CoordinatorOwnership`, one trusted scope and `AuthorizeSkillRegistryChange`. Expose only the read adapter to `ApprovedSkills`, not the writer or its authorizer. `writeAuthorized({scope,expectedRevision,operation,pin})` is **not** an authenticated HTTP handler or a model tool.

Ownership fencing is not user authorization. The injected synchronous authorizer must be installed by the authenticated registry owner/common-gate integration, never by a manifest, client payload, model or plugin. The writer calls it afresh **after acquiring the repository writer lock**, supplying an immutable exact request. It must reject unless that exact scope/operation/pin/revision is currently authorized and return nonsecret `actorId` and `authorizationId` audit references. No authorization result is cached. It must not perform external IO, start asynchronous work, or execute effects inside the database transaction. Async common-gate decision acquisition belongs outside this transaction; the trusted hook must recheck its validity/revision/identity under this boundary rather than blindly reuse an old approval. This is an injected authorization boundary, not a new policy engine or a shipped owner/gateway implementation.

The existing repository verifies ownership and epoch after its writer-lock wait and fences transaction operations/commit. The writer additionally checks active ownership around authorization and after both puts. Scope state uses exact CAS; audit creation uses expected revision zero. For each successful transition, the same transaction persists:

1. the new scope record and `op007.skills.registry.changed` event;
2. a new `op007.skills.registry-audit.v1` record keyed by `['op007.skills.audit',scope,newRevision]` and `op007.skills.registry.audited` event.

Audit metadata contains schema version, exact operation/pin/scope/expected revision, resulting revision, actor/authorization reference and owner epoch. The generic audit record supplies timestamp/revision. Audit conflicts or failures roll back the state, both events and cursor together. A replay with the old expected revision fails rather than silently applying again; no additional idempotency authority is introduced. The generic event payload contains registry metadata, so future subscriptions must apply authenticated scope filtering rather than expose the global repository feed.

## Integration, retention and recovery responsibilities

- This module never reads/writes/publishes bundle files. `ApprovedSkills` continues to verify exact manifest/resource hashes and returns inert verified bytes, not native Pi paths. Tests alone create disposable bundles.
- Server-owned roots **and ancestors** must be immutable to task/untrusted processes. Keep immutable version directories while any run/history references them. The existing portable Node path checks are not hostile-host confinement. Registry approval does not make roots immutable or verify bundle bytes: trusted staging must call `ApprovedSkills.inspect` and review the pin/content before authorizing approval.
- Rotation changes only new selections. Already selected versions remain usable while still approved and unrevoked. Revocation/deletion blocks subsequent loads, including the post-IO approval recheck; it cannot erase bytes already returned or model context. The final runtime effect still requires the common action gate and fresh grants/revocation checks.
- No schema migration is added. Parent integration must explicitly open/migrate the existing PostgreSQL repository, acquire fenced ownership, bind authenticated scopes and provide the authorizer. Dormant import alone does nothing. No HTTP, durable run selection rehydration, scheduler, UI, readiness authority or native skill path is wired here.
- Retained history/tombstones deliberately consume capacity; reaching the limit refuses new pins instead of evicting identity/revocation history. Audit history is append-only through this API and has no pruning policy in this slice. A future separately reviewed retention/backup plan must cover audit history and run references without resurrecting revoked identities.
- Disable new admission by deactivating active entries, revoke to block existing selections' subsequent loads. Restore an older approved version for new work by activating its retained pin, never by undoing a tombstone. Backup/restore must include registry/audit records and exact immutable bundles; stale database restoration must not resurrect post-backup revocations without reconciliation. No live migration/cutover/rollback is performed or qualified.
