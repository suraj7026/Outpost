## API contract

All times are integral UTC epoch milliseconds. Supported input timestamps: 1970-01-03 through 2099-12-29 inclusive, with envelope space reserved around the endpoints. Invalid requests throw schema/RangeError errors; parser invariant failure throws rather than pretending there is no work. No host timezone, current time or random value is consulted.

- `validateCalendarDefinition(unknown) -> CalendarDefinition`: strict `{kind:'cron', expression, timezone, gap:'skip', fold:'earlier'|'later'|'both'}`. Five minute-resolution fields, max 256 characters, whitespace normalized. A field-aware lexical gate permits comma-separated items: a numeric value (or case-insensitive JAN–DEC names only for month, SUN–SAT only for weekday), a range of field values, or `*`. Positive safe-integer steps apply only to wildcards/ranges (`*/15`, `MON-FRI/2`), not singleton values. Before Croner compilation, every atom and both range endpoints must be safe integers within the field's inclusive bounds: minute 0–59, hour 0–23, day 1–31, month 1–12, weekday 0–7. Case-insensitive names are checked in their own field; both Sunday aliases 0 and 7 remain valid. This includes endpoints that stepping would never visit and every comma-separated item. Names and aliases are not rewritten: Croner retains range ordering (including end-of-range SUN as 7), maximum step sizes (60/24/31/12/7 respectively), and recurrence evaluation. Steps may exceed the range span but not the field's maximum step size. No seconds/year input, macros, random/hash fields, custom `L`/`W`/`5L` modifiers, partial numeric tokens such as `0*`, or misplaced names. Day-of-month and day-of-week use **OR** when both are restricted, standard Sunday numbering. A required named IANA timezone (including UTC and aliases) must first have named-identifier syntax; Temporal then checks availability and any resolved numeric-offset identifier is rejected. Datetime strings, bracketed timezone annotations, and bare numeric offsets are rejected even though Temporal's wider input API accepts them. Named IANA entries such as `Etc/GMT+5` remain valid. Aliases retain their input spelling. No hidden default gap/fold policy.
- `previewCalendar(definition, {afterAt, throughAt, limit, candidateLimit?}) -> {occurrences, status, candidatesExamined}`: `(afterAt, throughAt]`, sorted by actual instant, not wall time. `limit` 1–100; positive horizon <= 8*366 days; `candidateLimit` 1–10,000 (default 10,000). Each slot is `{scheduledAt, wallTime, offset, fold:'unique'|'earlier'|'later'}`. `wallTime` is ISO civil time to seconds without offset. `horizon` means the entire requested window was exhausted (fewer than limit); `limit` means the requested prefix only. `search-limit` returns **no slots**, not an unsafe partial prefix, and must never advance a durable cursor. A `limit` result is not a complete due window. Empty horizon results mean no occurrence **within the bounded window**, not globally impossible forever.
- `calendarDefinitionDigest(definition) -> sha256`: versioned ordered tuple of normalized expression, timezone and DST policies.
- `identifyCalendarOccurrence(definition, binding, slot) -> CalendarOccurrence`: validates the slot actually matches the expression and DST policy; adds definition digest, immutable `{scheduleId, scheduleRevision, snapshotDigest}` and deterministic ID. Binding revision must be a positive safe integer; snapshot digest is lowercase SHA-256 of an externally resolved immutable instruction/skills/configuration manifest. Identity hashes a versioned ordered tuple of schedule ID/revision, definition digest and scheduled instant. Fold instants are distinct. A changed snapshot under the same revision **does not** create a fresh ID; it is a conflict for the repository to reject. Persist the returned pins and slot once; never recompute history after timezone database updates.
- `calendarEventIdentity({scheduleId, source, eventId}) -> sha256`: versioned tuple avoids delimiter collisions. Source must be a caller-authenticated account/connector namespace. Stable across schedule edits and receipt retries. It performs neither authentication nor persistence and does not accept a payload as authority. Store event identity independently of schedule revision so editing a schedule cannot bypass event deduplication.
- `calculateCalendarEligibility(definition, input, occurrences) -> {eligible, decisions, hold}`: pure advice for up to 1,000 occurrences; duplicate equal IDs collapse; conflicting rows sharing an ID throw. Current-definition IDs/slots are recomputed and checked. See exported `CalendarEligibilityInput`: immutable binding, now/previousObservedAt, revision `[effectiveFrom,effectiveUntil)` (`null` end), paused/revoked/cancelled, missed policy, on-time grace, max lateness, overlap policy, active run count, completeness flag and consumed occurrence IDs (max 10,000). No state is changed. `eligible` contains at most the newest due occurrence. Each unique input receives a typed reason; `hold` is null or the schedule-wide blocker.

### DST and bounded search

Croner evaluates **UTC wall-clock labels**, not zoned times; Temporal resolves those labels using the runtime IANA database. Nonexistent civil times are skipped, never shifted. Repeated civil times select earlier/later/both explicitly, including half-hour/two-hour changes and skipped whole days. Search starts 24 hours before the instant cursor and ends 24 hours past the horizon (IANA offsets are within 24h). An explicit finite Croner year range encloses that window, bounding even unreachable date searches. Candidate count bounds all external enumeration; prefix retention bounds memory. Before returning a prefix, search proceeds far enough that unseen wall labels cannot sort ahead of it. This handles cursors inside either side of a fold and requires strict advancement from the parser.

### Missed runs and eligibility

`skip` discards lateness greater than `onTimeGraceMs`; `coalesce` selects the newest due slot, provided lateness is at most `maxLatenessMs`. Both bounds are inclusive; grace must not exceed max lateness. Older slots never resurrect just because the newest already has a receipt, is overlap-blocked or is too late. Even within grace, at most one newest slot is selected (no burst catch-up). Max lateness is capped at 366 days. Overlap `forbid` rejects when the caller reports any active run, **including old-revision/unknown runs**; `allow` bypasses only that check, not admission capacity/budget/authority limits.

Pause, revocation, cancellation, backward observed clock movement, and incomplete windows fail closed. Clock-regression hold remains until trusted time reaches the persisted observation watermark; this module never lowers it. Forward wall-clock jumps cannot be distinguished from genuine downtime without an external trusted clock: max lateness and consumed-ID tombstones constrain recovery but do not prove clock correctness. `completeWindow` is an explicit caller assertion, not inferred from a prefix: integration must obtain a complete due window or keep it held. Very long/dense downtime that exceeds bounds requires a separately reviewed bounded cursor/coalescing strategy; do not silently drop work or evaluate a partial prefix as if complete.
