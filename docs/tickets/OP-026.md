# OP-026 — Subagent roles, launch contracts, and model ceilings

**Status:** Proposed · **Priority:** P1 · **Effort:** L · **Origin:** pi-subagents 0.83.0
**Dependencies:** OP-001, OP-007; develops OP-009's worker lifecycle alongside OP-028. OP-031 supplies richer Ollama model metadata, not a prerequisite for fixed-model launches.

## Problem and outcome
Outpost has worker primitives but no usable role registry or resolved child-launch preview. Users should be able to choose scout, researcher, worker, reviewer, oracle, or a reviewed custom role and see exactly what will run.

## Scope
Store versioned profiles containing purpose, instruction/skill references, allowed tools, context mode, model, thinking level, workspace constraints, and output contract. Default reviewers/scouts to read-only. Support fresh context and an explicit scoped parent-context fork; show what context is inherited. Resolve each launch to an immutable contract with role digest, exact provider/model, effective tools/extensions, scope, parent identity, budget reservation, and provenance. Add preflight that explains unavailable skills, credentials, models, incompatible runtime APIs, and denied required tools before any child starts.

Support per-role and per-run model selection within server-owned allowlists and thinking ceilings. A project/profile override can narrow but never replace the owner's authority ceiling. Nested delegation is off for ordinary leaves and requires an explicitly authorized coordinator role plus depth and cumulative-spawn limits.

## Safety and recovery
Outpost's loader currently exposes no extensions; installing pi-subagents in the developer's Pi does not enable it in Outpost. First qualify supported APIs against Outpost's pinned Pi SDK and either adapt explicit extension APIs or implement the contract natively. No ambient extension, credential, builtin shell, or filesystem-tool inheritance. Each child effect still enters `outpost_action` with child identity and inherited scope. Fuzzy model suggestions may assist selection, but execution pins an exact approved provider/model. Re-resolve and compare the contract at launch and resume; fail closed on drift.

## Acceptance criteria
- A read-only reviewer cannot mutate files through a tool, extension, nested launch, or alternate runner.
- Fresh/fork context modes preserve provenance and exclude unauthorized parent history.
- Per-run overrides cannot exceed model, thinking, tool, workspace, or budget ceilings.
- Missing/ambiguous profiles and unsupported SDK contracts fail before admission.
- Role changes do not silently alter already admitted children.
