# OP-030 — Opt-in watchdog review and delegation diagnostics

**Status:** Proposed · **Priority:** P2 · **Effort:** L · **Origin:** pi-subagents 0.83.0
**Dependencies:** OP-026, OP-028, OP-022, OP-017; extends OP-013 diagnostics.

## Problem and outcome
A child can finish normally while missing constraints, drifting in scope, or claiming tests it did not run. Independent bounded review should surface evidence-backed concerns without creating endless model loops or acting as a replacement permission system.

## Scope
Offer an opt-in watchdog with its own approved model and budget, distinct from the reviewer role. Trigger it at meaningful changed-code boundaries; add optional bounded tool cadence only after measuring cost. Feed a limited diff, explicit task constraints, selected tool evidence, and available local diagnostics. Never install language servers automatically. Persist structured findings with source, severity, importance, evidence, and proposed next action. Severity determines acceptance blocking; importance determines notification delivery.

Suppress unchanged/reverted diffs and repeated concerns. Stop automatic correction on stalemate or round/budget exhaustion and ask the owner. Add a delegation-doctor report showing resolved profiles, SDK compatibility, model/credential readiness, tool ceilings, extension launch intent, acknowledged runtime registration, and supervisor routing. Registration acknowledgement is not proof that an extension's tools are healthy.

## Safety and recovery
Do not transplant the extension's optional permission arbiter: its documented defaults allow unspecified tools and bypass bash, and `ask` is answered by a model rather than the human owner. Outpost remains fail-closed through its common exact-action gate. Watchdog findings are advice/evidence, not grants. Reject stale findings after revision changes and preserve unavailable-review states without claiming clean review.

## Acceptance criteria
- No changed evidence means no repeated boundary model call.
- Reviewer failures are visible and cannot be interpreted as approval.
- Stalemates and cost caps stop continuation deterministically.
- False test-success claims are flagged against actual execution evidence.
- Doctor is read-only; fixes and configuration changes require explicit commands.
