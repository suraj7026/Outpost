# OP-021 — Changed-files, diff, checks, and review workflow

**Status:** Proposed · **Priority:** P1 · **Effort:** L · **Origin:** T3 + Hermes review lanes
**Dependencies:** OP-019, OP-022, OP-018; OP-020 adds restore actions, not a prerequisite for read-only review.

## Problem and outcome
Outpost's revision-bound patch/check primitives need a usable review surface. A narrative “tests pass” should not substitute for current, inspectable execution evidence.

## Scope
Show task-scoped changed files, base/current revisions, unified or split diffs, untracked files, check commands, exit codes, and output artifacts. Allow review comments and request-changes with durable linkage to the inspected revision. Checks run against the intended worktree and record exact inputs. Distinguish local changes, committed changes, and published changes. Start with local review; PR creation/push is a later separately authorized integration.

## Safety and recovery
Invalidate review/check freshness after code changes. Sanitize rendered diffs and tool output; bound large/binary files with explicit exclusions. Approval of code quality does not authorize pushing, merging, or deployment. Preserve review history when a new run produces rework rather than overwriting the previous verdict.

## Acceptance criteria
- A successful check becomes visibly stale when its source revision changes.
- Review comments identify the exact revision and remain readable after rework.
- Large diffs remain bounded and clearly report omitted content.
- No push/merge/deploy happens through a generic “approve review” command.
