# OP-011 — Optional channel intake and reliable result delivery

**Status:** Proposed · **Priority:** P2 · **Effort:** XL · **Origin:** F11 + Hermes
**Dependencies:** OP-001, OP-008, OP-022; coordinate occurrence IDs with OP-004.

## Problem and outcome
Drafts, delivery-operation records, and notifications are useful primitives, not proof of integrated messaging providers. Optional channels should provide convenient intake without becoming a second trusted control plane.

## Scope
Implement one provider first with verified sender/account routing, conversation-to-task mapping, inbound deduplication, attachment limits, and durable delivery receipts. Separate drafting, approval, send claim, provider acknowledgement, and reconciliation. Preserve source identity and delivery destination in every run. Keep sensitive approvals on the signed Outpost clients unless an equally strong authorization flow is explicitly designed.

## Safety and recovery
Channel text and attachments are untrusted inputs. Do not infer authority from a display name or a quoted message. A timeout after send claim is unknown, not automatically retryable. Delivery failure must not rerun completed agent work. Verify provider signatures, replay windows, account revocation, and outbound destination before dispatch.

## Acceptance criteria
- Duplicate inbound events create one instruction with traceable provenance.
- Cross-account routing cannot expose another identity's task or artifacts.
- Crash tests cover pre-send, post-send/pre-ack, and durable acknowledgement boundaries.
- Retry/reconcile controls accurately distinguish failed from unknown delivery.
