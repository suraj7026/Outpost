# OP-014 — Attention inbox and evidence-oriented task board

**Status:** Proposed · **Priority:** P1 · **Effort:** M–L · **Origin:** F14 + Hermes review lanes
**Dependencies:** OP-001, OP-018, OP-022; OP-021 supplies coding review details.

## Problem and outcome
A task list and approval inbox do not fully explain which tasks need attention. Users should see blocked input, approval, review, failed verification, unknown effects, and normal queue waiting as different states.

## Scope
Build a projection of task lifecycle with focused filters and counts. Show the next required action, responsible actor, run age, latest evidence, and dependency blockers. Separate review from blocked work: implementation can be ready for review without being an execution failure. Provide approve/reject, request-changes, resume, cancel, and inspect-evidence actions only where supported by the server contract. Keep board movement a command, not a local visual state mutation.

## Safety and recovery
A drag to “done” cannot bypass verification or approval. Reconnecting clients reconcile server revisions rather than replaying optimistic transitions. Do not conflate a process exit, model completion, or downstream notification with successful task completion. Hidden/archived tasks must not continue unnoticed without explicit semantics.

## Acceptance criteria
- Every attention state has a clear next action and supporting evidence.
- Stale commands conflict visibly rather than overwriting newer lifecycle state.
- Review/rework loops preserve attempt history and current ownership.
- Counts and selected-task state converge after stream reset without loading all history.
