# OP-007 — Approved skills and task instruction profiles

**Status:** Proposed · **Priority:** P1 · **Effort:** M–L · **Origin:** F07 + T3/Hermes
**Dependencies:** OP-002; capability activation reuses existing catalogue controls.

## Problem and outcome
Outpost's Pi resource loader returns empty skill/extension/prompt/agent-file collections. A capability catalogue therefore does not currently imply usable runtime skills.

## Scope
Load an explicitly approved skill set through Pi, exposing compact metadata first and full instructions/references only when selected. Store source, content hash, version, readiness requirements, and activation state. Let users choose a task instruction profile or an explicit skill bundle; show the versions used in the task evidence. Initially profiles select instructions and configuration within one Outpost authority domain, not separate operator homes. Reject collisions and unsafe reference paths.

## Safety and recovery
Skills are instructions, not execution grants. Do not enable arbitrary native extensions, shell preprocessing, or credential inheritance merely because a skill requests them. Pin active versions per run; reviewed edits normally apply to subsequent runs, with immediate revocation available. Recheck required tools/credentials before scheduled use.

## Acceptance criteria
- A small approved skill can be discovered, invoked, and traced to its exact version.
- Missing requirements produce an actionable readiness state.
- Unapproved skills/extensions cannot enter the runtime through local directory discovery.
- Updating or revoking a skill has defined effects on queued and active work.
