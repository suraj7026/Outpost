# OP-022 — Verified completion and explicit run outcomes

**Status:** Proposed · **Priority:** P0 · **Effort:** L · **Origin:** T3 + Hermes; strengthens all original features
**Dependencies:** OP-001 for durable run identity; can design verification contracts in parallel.

## Problem and outcome
Outpost normally ends successful model turns in `verifying` or `waiting_for_approval`. A finished turn is not a completed task. Define who verifies the result and what evidence permits a terminal success state.

## Scope
Separate input, attempt/run, verification, review, and task outcomes. Record structured completion proposals with goal criteria, produced artifacts, check results, unresolved effects, and required reviewer. Add bounded verification actions and explicit success, failed verification, needs input, needs approval, cancelled, and unknown outcomes, mapping them deliberately to existing task states. Keep lifecycle transitions server-owned. A worker/model may propose success but cannot invent passing evidence.

## Safety and recovery
Require evidence freshness against relevant code/configuration revisions. Unknown external effects prevent unconditional success. A process that exits without a valid lifecycle result is interrupted/failed, not done. Reconciliation must finalize each attempt once while retaining late evidence without duplicating downstream delivery.

## Acceptance criteria
- Model text claiming completion cannot bypass required checks or approvals.
- Failed/stale/missing verification produces an actionable non-success state.
- Crash between result persistence and task projection converges to one finalization.
- Review/rework preserves prior attempts and does not rerun external effects automatically.
