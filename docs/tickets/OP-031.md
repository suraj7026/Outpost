# OP-031 — Ollama Cloud model discovery and capability-aware selection

**Status:** Proposed · **Priority:** P1 · **Effort:** L · **Origin:** pi-ollama-cloud 0.13.1
**Dependencies:** Existing inference configuration; OP-003 for failure handling and OP-002 for context limits. Feeds OP-026 role selection.

## Problem and outcome
Outpost already supports direct Ollama-compatible inference and a thinking-capability probe. The missing feature is a trustworthy provider catalogue and capability-aware model picker, not first-time Ollama support.

## Scope
Keep local/self-hosted Ollama-compatible endpoints distinct from direct Ollama Cloud. Discover Cloud model IDs and per-model metadata, retaining a versioned last-good snapshot and explicit first-launch fallback. Filter unsuitable/non-chat protocols and require tool capability for action-running roles. Display model identity, modalities, context/output limits, supported thinking choices, source of each limit, freshness, and readiness. Offer bounded background refresh and explicit force-refresh with cancellation and diagnostics.

Qualify provider compatibility flags and streaming behavior against Outpost's pinned SDK. Preserve full provider/model identity for parent, reviewer, and worker selections. Map supported thinking values per model; do not equate a boolean capability with support for every level or a working off switch. Generated/probe-derived limits are evidence with dates, not live guarantees.

## Safety and recovery
Catalogue refresh must not switch active tasks, alter approved model routes, erase a healthy snapshot on partial failure, or silently redirect Cloud requests to a local server. The installed implementation throws on partial refresh after retaining its last-good baseline; adopt explicit incomplete-state reporting. Keep credentials server-owned, never copy the developer's Pi auth file. Live probes are opt-in/budgeted requests, not a hidden side effect of every picker render.

## Acceptance criteria
- Offline startup, partial metadata failure, cancellation, and stale refresh races preserve usable known state.
- Removed/incompatible models are marked unavailable without silently substituting another provider.
- Model selection respects child scope/ceiling rules and reports requested versus resolved thinking.
- Tool streaming, usage, cancellation, malformed responses, and overflow behavior are covered by compatibility tests.
