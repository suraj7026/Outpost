# OP-037 — Resource-aware worker placement with durable admission

**Status:** Proposed · **Priority:** P1 · **Effort:** L · **Origin:** T3 host-load-balancing rescan `2c119bd9`
**Dependencies:** OP-001, OP-009, OP-017, OP-019 for coding workspaces. Uses existing authenticated hosts first; does not require independent-environment federation.

## Problem and outcome
Outpost has two fixed execution hosts, not a placement policy or replicated coordinator. Users should choose a host explicitly or allow new eligible work to be placed according to capacity, preference, and locality under one authoritative ledger.

## Scope
Register approved host capabilities, workspace/revision readiness, provider/model availability, effective resource limits, and fresh CPU/memory telemetry. Add Manual only / Less often / Normal / Prefer settings and explain why a candidate was selected or excluded. Treat T3's weighted CPU/memory score as a starting heuristic, not a guarantee. Include active reservations, queue depth, model/browser/process slots, and verified GPU/VRAM limits only when available. Account for container/cgroup limits rather than blindly using whole-host capacity.

Perform selection and reservation atomically at the coordinator, recheck at dispatch, and pin the admitted task/run to its owner. Explicit worktree, files, attachments, credentials, and data boundaries constrain placement. A matching repository name is not evidence of matching commits, uncommitted state, or dependencies. No usable capacity means queued/manual/blocked, never silent placement on an unsafe host.

## Safety and recovery
T3's implementation is client-side selection of new drafts, off by default, not reserved distributed scheduling. Outpost must prevent simultaneous clients selecting the same apparently idle capacity without reservation. Stale/unknown telemetry cannot mean unlimited capacity. A dead/disconnected worker may still be running; fence ownership and reconcile before reassignment. Network-route failover is not execution failover, and active tasks do not migrate automatically.

## Acceptance criteria
- Concurrent submissions cannot exceed configured host/model/browser capacity.
- Stale, future-skewed, invalid, saturated, unauthorized, and incompatible candidates are excluded with reasons.
- Manual host/branch/worktree selection remains stable; automatic selection is visible before dispatch.
- Restart recovers reservations without duplicate ownership; unknown execution blocks unsafe reassignment.
- Two worker hosts never imply two writable coordinators or SQLite HA.
