# OP-004 — Calendar/event automations with admission recovery

**Status:** Proposed · **Priority:** P1 · **Effort:** L · **Origin:** F04 + Hermes
**Dependencies:** OP-001, OP-003, OP-013, OP-022; delivery integrates with OP-011.

## Problem and outcome
Outpost has interval/one-shot scheduling, not a complete calendar-aware automation product. A timezone field alone does not implement DST-safe wall-clock recurrence.

## Scope
Support explicit timezone-aware cron/calendar recurrence and authenticated event triggers. Show a preview of upcoming occurrences before enabling. Define overlap, missed-run grace, catch-up/coalescing, deduplication, and per-job runtime/cost limits. Pin the resolved instruction/skill/configuration revisions to each occurrence. Preflight credentials, tools, workspace, and delivery prerequisites; expose blocked configuration without making an LLM call. Separate schedule, occurrence, admission, execution, and delivery records.

## Safety and recovery
A completed execution recovered from a durable receipt is not rerun merely because delivery failed. An ambiguous external send remains unknown. User pauses must not be overridden by recovery. Webhook payloads are untrusted data, not shell scripts or authority. Prevent recursive schedule creation by unattended jobs unless a separately approved capability permits it.

## Acceptance criteria
- Tests cover DST gaps/folds, timezone changes, downtime, overlap, duplicate events, and cancellation.
- Failure after each admission/delivery boundary preserves occurrence identity.
- One alert is emitted per blocked-config episode; recovery clears the episode explicitly.
- A paused/revoked schedule cannot dispatch through a stale worker.

## Delegated-workflow extension integration
The requested pi-subagents [missions/schedules](../../../../.pi/agent/npm/node_modules/pi-subagents/docs/missions.md) add recurring workflow templates, pinned script/argument snapshots, quiet outcomes, and mission-linked state. Route those concepts through this scheduler and OP-027/OP-028, not a second extension scheduler. Explicitly decide whether closing a task revokes its schedules; upstream mission closure and goal-notice budgets do not automatically stop scheduled launches. Outpost admission budgets and pending owner decisions must be enforced independently at each fire.

## Connect-style offline webhook intake
The [30 October T3 rescan](../T3-REMOTE-CONNECTIVITY-ANALYSIS.md) adds optional broker-held webhook delivery through OP-036. Keep this opt-in: the broker stores sensitive bodies and token-bearing paths, so require explicit retention/size limits, encrypted storage/access controls, and deletion on unlink. Persist the delivery ID at destination admission before execution; retries after a lost acknowledgement must deduplicate there, not assume an HTTP timeout means nothing ran. Destination signature/token verification remains mandatory. Reference: [T3 held inbox](../../../t3code/infra/relay/src/hooks/HookInboxObject.ts), [forwarder](../../../t3code/infra/relay/src/hooks/HookForwarder.ts).
