# OP-015 — Paired execution nodes and local companion

**Status:** Proposed · **Priority:** P3 · **Effort:** XL · **Origin:** F15
**Dependencies:** OP-001, OP-013, OP-017, OP-022; independent security review before activation.

## Problem and outcome
Outpost already executes authenticated root commands on two configured hosts. This ticket is not “add remote execution”; it is a later move to explicit node identity, capability-based routing, and revocable ownership.

## Scope
Define pairing, node keys, advertised capabilities, heartbeat, permitted filesystem/process scope, and revocation. Bind each dispatched job to a node identity and action digest, with durable receipts and artifact provenance. A local companion may expose narrowly scoped desktop resources only with explicit user consent. Begin with a single least-privileged capability and a visible connection/activity status.

## Safety and recovery
Pairing does not grant unrestricted root access. Do not reroute a failed job to another host if the action's authority or data boundary changes. A disconnected node may have executed an action; reconcile its receipt before retrying. Expire leases and fence revoked node keys. Avoid turning the companion into a generic user terminal or remote desktop product.

## Acceptance criteria
- Revocation prevents new dispatch and invalidates stale leases.
- A job cannot execute on a different node than its approved identity.
- Network partition/reconnect tests preserve unknown outcomes without duplicate effects.
- Node credentials and private local files never appear in routine diagnostics.
