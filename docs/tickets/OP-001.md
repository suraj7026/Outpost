# OP-001 — Durable input queues and run admission

**Status:** Proposed · **Priority:** P0 · **Effort:** L · **Origin:** F01 + T3
**Dependencies:** None; coordinate event contracts with OP-018 and finalization with OP-022.

## Problem and outcome
Outpost persists instructions but lacks a complete queued-input delivery contract across the ledger/Pi boundary. Users must be able to distinguish accepted, waiting, delivered, running, cancelled, and uncertain work after a reconnect or restart.

## Scope
Persist an input ID, idempotency key, sequence, source actor, authority reference, requested mode, and delivery receipt before acknowledgement. Start with explicit steer and follow-up modes; stop-and-replace must be a separate user action. Serialize turns within a task while admitting independent tasks through bounded model/browser/host capacity pools. Display queue order and the limiting resource. Reject overflow visibly; do not silently discard instructions. Reuse the existing transaction/outbox rather than transplanting T3's store.

## Safety and recovery
Record the distinction between dispatch intent and confirmed runtime receipt. On an ambiguous crash, reconcile rather than blindly resubmit a potentially executed action. Cancellation fences promotion of queued work; revoked authority is checked again at execution. Queue edits are revision-checked commands.

## Acceptance criteria
- Concurrent device submissions deduplicate and preserve deterministic delivery order.
- Crash injection before/after persistence and runtime admission never creates two active owners for one session.
- Cancelling a queued input survives restart without cancelling unrelated work.
- Capacity/fairness tests demonstrate bounded concurrency and no indefinite background starvation.
