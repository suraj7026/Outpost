# OP-005 — Quiet monitors and bounded standing programs

**Status:** Proposed · **Priority:** P2 · **Effort:** L · **Origin:** F05
**Dependencies:** OP-004, OP-017, OP-022; use OP-010 for deterministic probes.

## Problem and outcome
The existing change-hash primitive can support useful monitoring, but repeated autonomous prompts would create noise, cost, and unclear authority. Users need explicit monitors with a clear reason for every notification.

## Scope
Define a monitor's source, expected condition, observation cadence, comparison policy, quiet hours, escalation target, expiry, and budget. Prefer deterministic/read-only probes before model interpretation. Persist observations and normalized change hashes; distinguish unchanged, changed, failed observation, and uncertain result. A standing program may propose follow-up tasks but should not inherit unrestricted execution rights. Provide pause, test-now, last-success, next-check, and notification-history controls.

## Safety and recovery
Apply cooldown and deduplication to repeated conditions without hiding a worsening incident. Use a bounded catch-up policy after downtime. A failed probe is not evidence that the monitored service is healthy. Do not include secrets from response bodies in alerts. Revalidate authority before any remediation action.

## Acceptance criteria
- Repeated unchanged observations remain quiet; meaningful changes emit one traceable alert.
- Quiet hours, expiry, pause, and budget exhaustion work across restart.
- Failed probes display degraded visibility rather than a false all-clear.
- Unattended remediation outside approved scope enters approval instead of executing.
