# OP-034 — Stable server identity and multi-route connection failover

**Status:** Proposed · **Priority:** P1 · **Effort:** L · **Origin:** T3 rescan `2c119bd9`
**Dependencies:** OP-018; integrate pairing/revocation with existing signed-device policy. OP-035/OP-036/OP-039 provide optional routes.

## Problem and outcome
Outpost's desktop saves an endpoint and protects pending signed commands from being sent to another server. Users need LAN/private HTTPS, SSH, and optional managed-tunnel routes to one logical server without duplicate tasks or accidental credential disclosure.

## Scope
Introduce stable server identity bound to a trusted key, ordered routes with provenance, active-route permission/status views, and manual add/reorder/remove. Treat discovered addresses as hints. Check destination identity before sending credentials; use TLS/key verification rather than trusting a public ID alone. Connect through a working route, preflight higher-priority alternatives before switching, and use cooldowns/jitter to avoid flapping. Preserve user routes while retiring stale learned ones and credential-dependent routes after their source is removed.

Keep one connection/retry owner per logical server. Coordinate snapshot watermarks and stream replacement with OP-018; credential renewal must not unnecessarily destroy a healthy stream. Show failures by stage: local network, broker/link, tunnel, host service, authorization, compatibility, synchronization.

## Safety and recovery
Retain HTTPS or loopback HTTP; do not downgrade a credential onto plain LAN HTTP. Permissions belong to the active session/route, never the union of all saved routes. Route failover changes transport to the same server, not task execution ownership. Pending commands retain idempotency and server/action identity; reconcile unknown effects rather than resend them blindly. Removing a route and revoking its authorization are distinct explicit actions.

## Acceptance criteria
- A reused LAN address or wrong server key receives no credential or pending command.
- Switching routes refreshes permissions and converges stream state without duplicate execution.
- A denied/flaky preferred route cannot repeatedly displace a healthy session.
- Restart, sleep/resume, route removal, and credential expiry preserve pending-command safety.
