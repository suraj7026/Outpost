# OP-027 — Parallel workflows, review loops, and advisor councils

**Status:** Proposed · **Priority:** P1 · **Effort:** L · **Origin:** pi-subagents 0.83.0
**Dependencies:** OP-009, OP-026, OP-028, OP-022; OP-019 for parallel writers and OP-029 for blocking decisions. Shares deterministic host-step execution with OP-010.

## Problem and outcome
A collection of worker launches is not a reliable multi-agent workflow. Users want scout → worker → independent reviewers → bounded fixes, parallel audits, and second opinions without managing every child manually.

## Scope
Introduce versioned workflow templates with stable step keys, dependency sequencing, bounded parallel fan-out/fan-in, conditional follow-up, structured output schemas, artifact bindings, and explicit stop conditions. Separate independent lanes so one blocked lane can stop without discarding siblings' results. Offer dry validation before launch and display the resolved plan. Bind reused results to workspace/input revisions; a previous “tests passed” receipt is not automatically current evidence.

Include bounded review loops with fresh reviewers and a configured maximum round count. Add an optional read-only council: independent initial reports from two or three advisors, curated disputed claims, one cross-examination by default, and a parent-authored decision memo recording evidence, disagreements, confidence, and unresolved owner decisions. Retained-session cross-examination and fresh-context fallback must be labeled differently. Consensus does not authorize implementation.

## Safety and recovery
Prefer reviewed templates over arbitrary script execution initially. If a script API is introduced, deny filesystem, network, shell, and host globals; host steps require separately granted concrete actions. Isolate parallel writers in managed worktrees. Reserve aggregate budgets before launches: upstream completed-child usage accounting alone does not cap already-running siblings. Infrastructure failure stops the lane; never silently switch execution mode or provider.

## Acceptance criteria
- Dependency ordering, partial lane failure, duplicate keys, bounded fan-out, and cancellation are tested.
- Structured verdicts—not parsed reviewer prose or a successful launch receipt—control subsequent steps.
- Review/council loops stop at their cap or an owner decision, preserving dissent and evidence.
- Restart reuses only eligible completed steps and cannot replay unknown mutations automatically.
