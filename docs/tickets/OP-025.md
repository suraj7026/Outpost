# OP-025 — Isolated programmatic tool execution feasibility gate

**Status:** Proposed research gate · **Priority:** P3 · **Effort:** XL if implemented · **Origin:** Hermes
**Dependencies:** OP-008, OP-010, OP-017; threat model and isolation decision required before implementation.

## Problem and outcome
Multi-step data processing can waste context by returning every intermediate tool result to the model. Programmatic composition may help, but running model-written code on Outpost's privileged hosts would create a serious policy bypass.

## Scope
First produce a threat model and prototype confined, read-only processing with fixed CPU, memory, time, filesystem, output, and network limits. Compare it with deterministic recipes. If justified, expose a narrow RPC tool interface whose requests use the same concrete-action gate as normal calls. Store full intermediate evidence outside model context under retention controls and return a bounded result summary. Keep the feature disabled until confinement is demonstrated.

## Safety and recovery
A subprocess, temporary directory, or private socket is not an OS sandbox. The executor must not read host credentials, open arbitrary network connections, spawn unrestricted descendants, or reach the ledger directly. Cancellation kills the process tree and fences late RPCs. Each mutation requires its own approved concrete action; approving the script cannot authorize unknown future effects.

## Acceptance criteria
- Adversarial tests attempt filesystem escape, credential access, direct network calls, runaway children, and late RPC use.
- The prototype proves bounded output/resource consumption and auditable per-call policy enforcement.
- If confinement cannot be demonstrated, record a no-go decision rather than ship host execution.
- Benchmark context savings against recipe execution; publish limitations, not only happy-path speed.
