# OP-019 — Task-owned worktrees and workspace lifecycle

**Status:** Proposed · **Priority:** P1 · **Effort:** L · **Origin:** T3 + Hermes
**Dependencies:** OP-001, OP-013; OP-022 defines terminal ownership release.

## Problem and outcome
Repository inspection and patch application do not isolate concurrent coding tasks. Users need a clear association between task, repository, base revision, branch/worktree, and active writer.

## Scope
Create a managed task workspace with explicit base commit, canonical path, branch identity, owner lease, setup state, and retention policy. Detect overlapping paths and shared workspaces. Preview setup hooks before execution and gate them as concrete actions. Show dirty/untracked state and offer explicit keep, archive, or clean-up after review. Preserve worktree ownership across restart and expose orphan reconciliation.

## Safety and recovery
One writer per worktree; parallel writers require separate worktrees. Canonicalize paths and defend against symlink/path changes. Never run repository-provided setup scripts merely because a worktree was opened. Cleanup refuses dirty or externally owned trees without an approved plan. A missing volume is not proof a workspace was intentionally deleted.

## Acceptance criteria
- Two simultaneous coding tasks receive distinct workspaces or an explicit shared-read-only mode.
- Lease loss and restart cannot create two active writers.
- Dirty cleanup, path overlap, setup failure, and branch collision are visible recoverable states.
- Every patch/check artifact identifies the actual worktree and revision.
